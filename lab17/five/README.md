# Часть 3. Односторонний чат и Модульное тестирование на Си (Оценка 5)

В данной папке находится финальная часть лабораторной работы: реализация потокобезопасного IPC-чата "Производитель-Потребитель" и модульные тесты для верификации работы разделяемой очереди. Весь проект реализован исключительно на языке **C**.

## 1. Архитектура чата «Производитель-Потребитель» (Задание 10)

Многопоточный асинхронный чат реализован в монолитном файле `queue_chat.c`. Взаимодействие между Клиентами (производителями) и Сервером (потребителем) организовано через глобальную структуру `msg_queue_t`.

### Механизм синхронизации и управления памятью:
* **Кольцевой буфер (FIFO):** Очередь сообщений построена на статическом двумерном массиве `messages[10][128]`. Потоки синхронизируют указатели чтения (`head`) и записи (`tail`) с переходом через ноль по формуле `(index + 1) % QUEUE_SIZE`. Это избавляет от необходимости сдвигать элементы в памяти при каждом чтении.
* **Потокобезопасность (Mutex & Condition Variables):** Доступ к разделяемой памяти полностью изолирован и защищен мьютексом `q.lock`.
  * **Защита от переполнения:** Если клиенты отправляют слишком много сообщений и очередь заполняется (`count == 10`), поток-клиент блокируется внутри функции `msgSend()` на кондишене `q.not_full`, уступая процессорное время серверу.
  * **Защита от чтения из пустой очереди:** Если буфер пуст (`count == 0`), поток-сервер блокируется в функции `msgRecv()` на условной переменной `q.not_empty` до тех пор, пока не придет сигнал `pthread_cond_signal` от любого из отправителей.
* **Жизненный цикл программы:** Потоки клиентов (`Klient_1` и `Klient_2`) инициализируют массивы строк, перемешивают их случайным образом, отправляют по 5 сообщений через `msgSend()` и завершают выполнение. Поток сервера работает асинхронно в бесконечном цикле и отсоединен от основного процесса с помощью `pthread_detach(tid_server)`. 
  Главный поток `main` дожидается окончания работы клиентов через `pthread_join()`, дает серверу дочитать остатки данных из буфера с помощью задержки `sleep(2)` и завершает процесс, уничтожая отсоединенный сервер автоматически без зависаний терминала.

## 2. Модульное тестирование

Для комплексной проверки логики работы разделяемой очереди без принудительного разделения исходного кода на множество мелких файлов был применен специализированный Си-фреймворк **Check**. 

Сборка тестов выполняется с флагом препроцессора `-DCHECK_TESTING`, который временно скрывает стандартную функцию `main` чата, позволяя фреймворку `Check` запустить собственный тестовый цикл.

### Описание тест-кейсов:
1. **`RegularUsage` (Тест базовой логики):** Эмулирует отправку стандартной строки в очередь и её мгновенное вычитывание сервером. Тест сверяет длину принятых данных и посимвольное равенство строк с помощью макроса `ck_assert_str_eq`, подтверждая целостность FIFO-структуры при передаче данных.
2. **`MessageTruncationCheck` (Граничный тест / Защита памяти):** На вход функции `msgSend()` подается заведомо длинное сообщение (200 символов). Тест контролирует работу функции `strncpy` внутри модуля: проверяется, что строка безопасно усекается до установленного предела `MSG_LEN - 1` (127 символов) и корректно закрывается терминальным нулем `\0`. Перед чтением буфер принудительно очищается через `memset()`, что гарантирует отсутствие мусора из памяти и подтверждает успешную защиту от переполнения буфера (Buffer Overflow).

### Результаты выполнения тестов (Вывод фреймворка Check):
При компиляции и запуске модульных тестов фреймворк выдает строго форматированный отчет прямо в консоль:

```bash
gcc test_queue.c queue_chat.c -o run_tests -DCHECK_TESTING -lcheck -pthread -lrt -lm -lsubunit$ ./run_tests
Running suite(s): Queue_Chat_Tests
100%: Checks: 2, Failures: 0, Errors: 0
```
### Сборка и запуск:
```bash
